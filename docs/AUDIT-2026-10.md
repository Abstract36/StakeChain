# STACH contract — internal audit & hardening (2026-10-28)

Scope: `contracts/contracts/Token.sol` (STACH, ERC20 + flexible/locked staking), as recovered from `Stakechain-Contracts-main.zip` (2022).

## Critical findings (fixed)

### C-1. `transferFrom` subtracted from the recipient
```solidity
balances[to] = balances[to] - tokens;   // was: minus instead of plus
```
Any `transferFrom` either reverted (fresh recipient, 0.8 underflow) or **destroyed the recipient's balance** while also debiting the sender — tokens vanished. Every DEX, router, or escrow integration was broken.
**Fix:** shared `_transfer` helper with correct credit, explicit allowance check, infinite-approval support, correct event.

### C-2. Unbacked reward payouts
`withdrawRewards()` did `balances[msg.sender] += rewards` while the 3M reward pool existed only as a counter — no tokens were ever credited to the contract. The sum of all balances could exceed `_totalSupply` (core ERC20 invariant broken), and payouts emitted no `Transfer` events, so explorers/indexers never saw them.
**Fix:** the constructor now carves a real 3,000,000 STACH reserve out of the 42M supply into `balances[address(this)]` (initial holder receives 39M). Withdrawals pay out of that reserve, are capped by it, and emit `Transfer`. Regression test asserts `sum(balances) == totalSupply()` after withdrawal.

## Medium / hardening (fixed)

- **M-1.** `approveAndCall` makes an arbitrary external call — now `nonReentrant`.
- **M-2.** `unstakeLocked`, `unstakeFlexible`, `withdrawRewards` had no reentrancy guard — added (defense in depth; staking entry points already had it).
- **M-3.** No zero-address checks on transfers — added (`transfer(0)` burn path removed; `totalSupply()` retains the `balances[address(0)]` subtraction for compatibility).
- **M-4.** `hardhat/console.sol` imported in production code — removed.
- **M-5.** Stake functions measured "deflation" via self-balance deltas around a self-call to `transfer()` — pointless for a non-deflationary token and fragile; replaced with a direct `_transfer`.
- **M-6.** No events for stake/unstake/reward lifecycle — added `Staked`, `Unstaked`, `RewardsWithdrawn`, plus `Transfer` events on all contract↔user moves.

## Accepted / documented behavior (unchanged)

- Rewards accrued while total pool weight is zero are never distributed (documented corner case; they simply stay in the reserve).
- `stakeInLocked` requires `lockUntil <= periodFinish`: locked staking naturally sunsets at the end of the 360-day program.
- `rewardsDuration = 360 days` ("1 year" of 12×30 days) — kept to preserve the original emission schedule and test vectors.
- Reward math (Illuvium-style `yieldRewardsPerWeight` / `subYieldRewards` accumulator) verified against the original 18-test suite — all pass unchanged.

`npx hardhat test`: **25 passing** — 18 original tests (untouched) + 7 fortress regression tests (`test/fortress.js`).

## Post-deploy pass: auditlens + slither (2026-10-28)

`auditlens scan` (static-first lens pass): **0 heuristic hits** at any
severity. Slither detector hits, triaged per exploitability-triage 54.1:

- `unchecked-transfer` in `Recovery.constructor` — one-shot rescue already
  executed on mainnet; STACH `transfer` reverts rather than returning false.
  Dead code path, neutralized.
- `divide-before-multiply` in `stakeInLocked` weight math
  (`duration*1e6/180d * amount`): rounds the lock fraction down by ≤1 part
  in 166,666 (~0.0004% weight underpayment to the staker, never over).
  Accepted precision loss, documented.
- `incorrect-equality` (`pendingYield == 0`) — early-exit guard, exact zero
  intended.
- `reentrancy-events` in `Faucet.drip` — state (`lastDrip`) updated before
  the external call (CEI held); only the event ordering trips the detector;
  token has no transfer hooks.
- `timestamp` family — inherent to time-based staking; no sub-second
  precision assumptions anywhere.

MUB classes (54.2) re-checked manually: no price oracles exist, all staking
state transitions are single-transaction atomic, and the
`subYieldRewards`/`yieldRewardsPerWeight` update order was the subject of
the original review above.

## Reported externally: reward accumulator truncation (2026-11-02)

Reported unsolicited by Nordin Sabli of KupiaSec (sec.kupia.io), who read the
contracts from the public repository. Verified here before replying, with the
numbers measured rather than taken: `contracts/test/reward-truncation.js`.

**The mechanism.** `_syncPool` advances `lastUpdatedTime` on every call, but
what it adds to `yieldRewardsPerWeight` is an integer division:

```
increment = secondsPassed * rewardsRate * 1e12 / totalLockedWeight
```

The remainder is not carried. A flexible stake weighs `1e6 * amount`, so one
STACH is 1e24 of weight, and at the flexible rate of 32,150,205,761,316,872
wei/s the increment is about `32,150 * seconds / STACH staked`. The loss is
therefore proportional to how often the pool is synced, and `processRewards()`
is `external` with no access control and no stake requirement — anybody can
sync both pools every block.

**Measured against live state** (read 2026-11-02, 24,500 STACH in the flexible
pool, weight 2.45e28):

| sync interval | accrued | exact | lost |
|---|---|---|---|
| 2 s (one Base block) | 603 | 789 | **23.57%** |
| 12 s | 15 | 15.75 | 4.7% |
| one 600 s step | — | — | ~0 |

Above `seconds * 32,150` STACH — 64,300 at a two-second interval — the
increment is zero while the seconds are still consumed. The test pins that at
70,000 STACH staked: time moves, the accumulator does not.

**Where the money goes.** The skipped emission stays in the reward reserve.
The token has no owner and no upgrade path, so it is stranded rather than
delayed — nobody can redistribute it. The test asserts that too.

**Corrections to the report, both ways.** The 64,000 figure is the point of
*total* loss, not where loss begins: at today's stake a frequent sync already
loses a quarter. Conversely, the locked pool does not simply "reach zero at
roughly twice the stake" — its rate is 2x but its weight multiplier is
1e6–2e6 depending on lock length, so the threshold is 64,300 STACH-equivalent
for a one-year lock and up to 128,600 for the shortest. At the live locked
weight (5.25e27) the loss is 2.0% per two-second sync. And in practice very
little has been lost so far: `lastUpdatedTime` was 3.2 days stale when read,
because nothing syncs these pools often. The defect is live but dormant, and
it gets worse as deposits grow — which is the perverse part.

**Fixed in source, 2026-11-02 — not on the live instance.** `_syncPool` now
carries `secondsPassed * rewardsRate * 1e12 % totalLockedWeight` into the next
sync, in `flexibleRewardRemainder` / `lockedRewardRemainder`, so the division
runs against an accumulated numerator instead of a fresh one. The emission no
longer depends on sync frequency at any stake size, which closes the griefing
vector along with the drift: `contracts/test/reward-truncation.js` shows 300
two-second syncs and one 600-second sync both reaching 789, where before the
fix they were 603 and 789.

The remainders are separate variables rather than fields on `PoolData`, so the
`flexiblePool()` / `lockedPool()` getters keep the four-value shape that
`api/stach.js` reads.

Widening `REWARD_PER_WEIGHT_MULTIPLIER` from 1e12 to 1e27 was the alternative
and would also divide cleanly. It is not unsafe — an earlier draft of this note
claimed it left only ~2.8x of overflow headroom, which was wrong: that figure
assumed a pool sitting at a dust weight, and both pools require a minimum stake
of 1 STACH, which floors the weight at 1e24 and leaves ~2.8e18x. The reason to
carry the remainder instead is that it conserves the emission by construction
rather than by having enough decimal headroom, and changes no magnitudes at
all. A wider multiplier only moves the threshold.

**The deployment is unchanged and unchangeable.** The token, the pools and the
3M reserve are one immutable contract at `0x82c5…7166` with no owner and no
proxy, so the live pools still truncate. `hardhat verify` of the current source
against that address will no longer match; the header of `Token.sol` says so.
For the live instance the only lever is sync frequency — and the pools are
synced rarely, which is why little has actually been lost.

This supersedes the note above that treated `divide-before-multiply` in the
weight math as the precision issue in this contract. That one costs 0.0004%;
this one costs a quarter of the emission at a two-second sync. Recording the
smaller one as accepted while missing the larger one is the actual finding.
